# Production readiness re-audit — 20 August 2026

Audited at commit `dc7fdf6` on `claude/mortgage-client-platform-xsxg4g`:
16,600 lines, 111 endpoints, 137 automated tests.

Verification was by exercising the running application — HTTP requests, a real
browser, a live PostgreSQL database, and local servers speaking the real
protocols for Microsoft Graph, the Anthropic API, SMTP and S3 — not by reading
the diff.

**Recommendation: conditional GO.** Ready to hold client data once section F is
complete. The seven critical findings from the first audit are fixed; what
remains is operational, not architectural.

---

## A. Findings fixed

### Critical

| ID | Finding | Evidence it is fixed |
| --- | --- | --- |
| C1 | Documents unencrypted at rest | AES-256-GCM envelope encryption, rotatable keys. Stored file contains no `%PDF`, mode 0600; API returns the original bytes; a flipped byte gives 500, never content; 12 documents re-wrapped v1→v2 and still readable; removing the old key fails closed. |
| C2 | No tested backup | Archive covers every table plus the document blobs, checksum-verified on write. Test drill: back up → wipe database and document store → restore → row counts match, documents decrypt, audit chain verifies, new ids continue. |
| C3 | In-memory rate limiting | Counters in PostgreSQL via one atomic upsert. Tenth bad password → 429 with `Retry-After`; a spoofed `X-Forwarded-For` creates no bucket unless `TRUST_PROXY` is set. |
| C4 | Default administrator credential | `ADMIN_EMAIL` required; supplied passwords must meet policy, otherwise generated and shown once; account always starts `must_change_password`. `admin1234`, `admin`, `password`, `Password1`, `changeme` all 401. |
| C5 | Experimental `node:sqlite` | PostgreSQL via `pg`. Placeholders rewritten at the data layer; transactions bound into `AsyncLocalStorage`. Twelve concurrent creations → twelve unique file numbers. |
| C6 | AI review could send without consent | Three gates: server switch + DPA reference, brokerage setting, per-client consent. With any off, nothing is sent and the row records why. A retry cannot bypass them. |
| C7 | No multi-factor authentication | TOTP mandatory for staff, never waivable for admins, single-use recovery codes, replay protection, admin reset. Verified in a browser end to end. The password step alone issues no session. |

### High

| ID | Finding | Evidence it is fixed |
| --- | --- | --- |
| H1 | In-memory pagination | Filters, search, sort and `LIMIT/OFFSET` in SQL; dashboard scored and ranked in SQL. 28 clients: 25 per page, no overlap, out-of-range page clamped. |
| H2 | Weak login throttling | See C3. |
| H3 | Co-applicants saw each other's documents | Visibility derived per applicant. Cross-applicant document fetch and upload both 404; broker-set sharing makes them mutually visible and can be revoked. |
| H4 | No malware scanning | ClamAV before bytes are servable; production refuses to start without a scanner or an explicit decision to run without one. |
| H6 | Preview bypassed the download permission | Byte endpoint requires `documents.download` whatever the disposition. Assistant role: list 200 with `can_download: false`, preview 403, download 403. |
| H7 / H10 | No HSTS; abrupt shutdown | HSTS present over HTTPS; SIGTERM drains in-flight requests then exits 0. |

### Found and fixed during the re-audit

| ID | Finding |
| --- | --- |
| R1 | The application-wide `X-Frame-Options: DENY` also applied to document responses, so the in-app preview iframe was refused. Found by opening it in a browser; headers alone looked correct. |
| R2 | Documents would have been lost on Vercel — serverless filesystems are empty on the next request. Added an S3-compatible backend and a boot refusal. |
| R3 | Sentry redacted by key name only, so `DOCUMENT_ENCRYPTION_KEYS=… failed to parse` would have shipped the master key. Phone numbers passed too. |
| R4 | Staff session cookies used the client lifetime, outliving the server-side session by days. |
| R5 | Over-size uploads killed the socket, so the client saw a network error instead of the limit. |
| R6 | A backup archive could name an arbitrary table; identifiers cannot be parameterized. |
| R7 | SMTP addresses were interpolated into commands and headers unchecked. |
| R8 | Retention settings did nothing, and a rotated key could never be retired. |

## C. New risks introduced

| Risk | What limits it |
| --- | --- |
| Losing `DOCUMENT_ENCRYPTION_KEYS` destroys every document, including in backups | Keys must be backed up separately from the hosting account (F2). |
| Mandatory MFA can lock out the brokerage | Ten recovery codes plus administrator reset. A sole administrator who loses both needs database access — so keep two. |
| One runtime dependency where there were none | `pg` only; six transitive packages, zero known vulnerabilities. |
| Two storage backends, two code paths | Both behind one seam and both tested; the S3 path is tested against a signature-verifying local server, not a real bucket. |
| A database write per API request for rate limiting | One upsert on a small table; at very high volume it becomes a hot row per IP. |
| 12-hour absolute staff sessions change daily habits | Intentional; see O8. |
| Restore is destructive | Explicit confirmation flag, verification before restoring, second flag in production. |

## E. Production GO / NO-GO

**Conditional GO**, subject to section F. Two qualifications on the record: the
remediation and this audit share an author (O2), and no integration has run
against a real provider tenant. The proportionate path is a controlled pilot of
three to five real clients for two weeks before opening the book.

## F. Exactly what remains

Before any real client data:

1. Provision the database; create the least-privilege role with `UPDATE`/`DELETE` revoked on `audit_log`; restrict network access.
2. Generate the encryption keys and back them up **outside** the hosting account.
3. Configure document storage for your platform, then confirm a document survives a restart.
4. Stand up ClamAV, or record an explicit decision to run without it.
5. Connect Microsoft 365, scope `Mail.Send` to one mailbox, diarise the secret expiry, and confirm a real email arrives.
6. Set `NODE_ENV`, `APP_URL`, `FORCE_SECURE_COOKIES`, `TRUST_PROXY`, `CRON_SECRET`; confirm `/ready` and the cron guard.
7. Create a second administrator.
8. Rehearse a restore into a scratch database by hand.
9. Get one independent review of the authorization model and encryption handling.

Within the first month:

10. Add CI running `npm test` against a PostgreSQL service container.
11. Enable breached-password checking (O7) and add a session-expiry warning (O8).
12. Have counsel confirm the consent wording (O6) and decide the retention windows and cross-broker visibility (O5).
